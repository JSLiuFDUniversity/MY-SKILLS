# 科研项目文件结构整理

## 触发条件

**仅由用户显式调用。** 用户提及整理文件、分类、归档、重构目录结构时启用。用户没有提出时不要主动整理——目录结构的稳定性对科研项目本身有价值，未经要求的重排会破坏协作者的心智地图和已有文档里的路径引用。

**触发后必须询问，这不是可选项。** 即使用户在本次会话中已授予全部权限、明确说"你随便动"、或此前批准过类似整理，仍要先给出方案并确认。理由：文件移动是本 skill 中唯一不可靠撤销的操作类别，且用户通常无法预估重排的影响面。授予权限解决的是"能不能做"，不解决"这样做对不对"。

## 第一步：只读勘查

先只读、不动手。收集：

- **目录树**：`ls` / `find` 各层，标注每层文件数量，找出平铺重灾区。
- **文件类型分布**：按扩展名分桶（文档、数据、代码、图、配置、压缩包、临时件）。
- **版本控制状态**：是否 git 仓库；哪些文件已跟踪、哪些未跟踪、哪些被忽略。**未跟踪文件移动后 git 不记录，无法用 `git checkout` 回退**，风险最高。
- **依赖关系**：搜索文件内容中的路径引用，找出哪些文件的相对位置是功能性的。
- **既有约定**：是否已有 `README`、`Makefile`、`pyproject.toml`、`.Rproj`、CI 配置、`paper/`、`data/` 等既定结构。既有约定优先于本 skill 的默认模板。
- **工作区规范**：是否存在 `.workspace-log/` 或类似留痕目录，整理操作本身同样需要被记录。

依赖关系排查命令示例：

```
# 找出所有引用了其它文件路径的地方
grep -rn --include="*.py" --include="*.R" --include="*.ipynb" --include="*.sh" \
     --include="*.md" --include="*.tex" --include="*.json" --include="*.yaml" \
     -E "(source|read_csv|read\.csv|open|load|include|input|import|\.\/|\.\.\/)" .

# git 视角：哪些文件是未跟踪的（移动不可回退）
git status --porcelain
git ls-files
```

## 第二步：产出整理方案

方案必须是一份用户能**在动任何文件之前就判断对错**的文档，至少包含：

1. **现状诊断**：问题在哪——平铺了多少文件、哪些类型混杂、哪些命名不一致。用事实描述，不做价值评判式吐槽。
2. **目标结构**：以目录树形式给出整理后的样子。
3. **移动映射表**：逐个列出 `原路径 → 新路径`，标出所属类别。用户要能逐行核对。
4. **不可动清单**：列出**不移动**的文件及原因。这是方案里最重要的部分——它证明你排查过依赖，而不是无差别搬运。
5. **风险提示**：哪些移动会破坏引用、需要同步改代码、或影响 git 状态。
6. **回退方案**：如何撤销（见下节）。
7. **提请确认**：明确说明在你得到答复前不会改动任何文件。

### 不可动清单（默认规则）

以下文件默认不移动，除非用户逐项确认：

- **依赖相对路径的程序文件**：被其他文件 `source` / `import` / `include` / 通过相对路径读取的脚本与配置。
- **构建与工程配置**：`Makefile`、`pyproject.toml`、`setup.py`、`package.json`、`.Rproj`、`requirements.txt`、CI 配置（`.github/workflows/`）。这些文件的位置本身就是语义。
- **版本控制元数据**：`.git/`、`.gitignore`、`.gitattributes`、`.gitmodules`。
- **被交付物按相对路径引用的资源**：稿件里 `\includegraphics{figs/fig1}` 引用的图片、报告里嵌入的图片与数据表。
- **入口文件**：`main.*`、`run.*`、`index.*`、`README.*`、`LICENSE`。
- **工作区留痕目录**（如 `.workspace-log/`）：其位置被规范固定。
- **隐藏文件与点目录**：工具链配置常是隐藏文件，移动会静默破坏环境。
- **用户明确标记为"别碰"的任何路径**。

判定含糊时一律放入不可动清单，并在方案中说明"我拿不准，需要你决定"。

### 默认目标结构（仅作起点）

```
project/
├── README.md              # 项目说明与目录导览
├── docs/                  # 说明文档、笔记、会议记录、审稿意见
├── manuscripts/           # 稿件、投稿材料、response letter
├── data/
│   ├── raw/               # 原始数据，只读，永不修改
│   └── derived/           # 清洗后/派生数据
├── analysis/              # 分析脚本（相互独立、可单独运行者）
├── figures/               # 最终图表
├── tables/                # 最终表格
├── references/            # 文献库、BibTeX、检索记录
├── admin/                 # 伦理审批、基金材料、合规文档
└── tmp/                   # 一次性工作区（可随时清空）
```

此结构按用途分层，与"数据只读、脚本可重跑、产出可定位"的科研习惯对齐。**但既有的项目约定优先**：若项目已有自己的分类法，沿用并只做增量整理，不要用这个模板覆盖它。

## 第三步：执行（仅在获得确认后）

1. **先建回退点**：
   - git 仓库：确认工作区状态，建议先提交或 `git stash` 现有改动；告知用户整理是一个独立可回退的提交。
   - 非 git 目录：在移动前生成一份路径清单文件（例如 `tmp/reorg-manifest-<时间戳>.txt`，含全部原路径与新路径），或按用户意愿做备份。**这份清单就是回退依据**，整理结束后按清理规范处置。
2. **按类别分批移动**，不要一次性重排。每批完成后核对文件数与清单一致。移动优先用 `git mv`（已跟踪文件），以保留历史。
3. **同步修正引用**：若方案中包含修改代码/文档中的路径，逐处修改并列出改动清单。引用修正与移动在同一批次内完成，避免留下断裂的中间状态。
4. **命名规范化**（可选，需在方案中单独列出）：统一大小写、空格改连字符、补零编号、日期用 ISO 格式。重命名比移动更容易破坏引用，除非用户要求，不要顺手做。
5. **验证**：
   - 移动前后文件总数守恒（除有意删除的）。
   - 抽查被引用的资源仍可被找到。
   - 若项目有构建/测试流程，跑一次确认没坏。
   - `git status` 结果与方案一致。
6. **整理后回执**：交付一份"做了什么"的说明——新建了哪些目录、移动了多少文件、改了哪些引用、留了哪些没动及原因、回退方法。同时按工作区规范写留痕记录。

## 与用户沟通的要点

- **方案要能一眼看懂。** 用目录树与映射表，不要用散文描述"我打算把文件按类型分成几个文件夹"。
- **明确"我没动什么"和"我动了什么"同样重要。** 未移动清单能让用户快速看出你是否理解了这个项目。
- **询问时给出可选项**：例如（a）按方案全量执行，（b）只整理文档类文件，（c）只整理无依赖的脚本，（d）先看我列的不可动清单再说。让用户能低成本地缩小范围。
- **用户只批了一部分就只做那一部分。** 不要把"部分同意"理解成整体授权。
- **用户否决后不要重新包装同一方案再问。** 记录否决理由，调整方向或停止。

## 边界

- 不删除文件。整理只做移动与重命名；发现冗余文件（重复副本、过期草稿）时列出并询问，不擅自清理。
- 不改文件内容，唯一例外是方案中已列明并经确认的路径引用修正。
- 不整理工作区之外的位置。
- 不为了"好看"创建空目录或占位文件。
- 与工作区整洁规范（工程文件清理与留痕）配合使用：整理动作本身属于工作区变更，必须留痕。

风险分类细则、依赖排查方法与典型失败案例见 `references/reorg-playbook.md`。
