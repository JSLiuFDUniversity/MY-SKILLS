# AI 内容审核闸门

科研与生产环境使用 AI 时，合规风险不在"是否使用了 AI"，而在**未经人工审核的 AI 产出被当作定稿对外发布**。本 skill 是一道闸门：所有 AI 生成或修改的交付物默认处于【待审核】状态，只有用户明确点名确认后，才升为【已审核通过】；未经审核的内容不得进入版本历史。

## 三条不可违反的规则

1. **默认【待审核】。** 凡由本 agent 创建或修改的交付物，在交付时刻一律标记为【待审核】。没有例外，不因"改动很小""只是格式化""内容我很确定"而降级。
2. **升级只能由明确指令触发。** 只有用户明确指定"哪个交付文件已确认通过"时，该文件才改为【已审核通过】。用户的沉默、先前对同类文件的批准、含糊的"看着还行""继续吧"都不构成审核通过。
3. **待审核文件不得 commit。** 提交前必须逐一核查，发现【待审核】文件即暂停提交，询问用户该文件是否已经审核。用户逐项确认后再执行提交。

**本 skill 常态生效**：只要工作区是 git 仓库（或存在跨会话交付物），无需用户提及即自动执行。开工时声明一次本次启用的规范，然后照做，不要为流程本身反复征求同意。

## 交付物边界

明确哪些文件需要标记，避免漏标与滥标。

| 需标记（交付物） | 不需标记 |
|---|---|
| 报告、稿件、摘要、回复信、基金材料 | 一次性工程文件（临时脚本、中间产物、缓存） |
| 图表、图片、示意图 | 用户提供的原始输入（原始数据、PDF、样本表） |
| 数据表、数据集、清洗后数据 | 版本控制与工具链配置（`.git/`、`.gitignore`、CI 配置） |
| 代码文件（分析脚本、管道、工具） | 第三方依赖与生成物（`node_modules/`、编译产物） |
| 演示与说明文档、README 中的实质内容 | 本 skill 自身的管理目录（`.ai-review/`） |

判定问题：**这个文件会离开本项目被他人阅读、使用或依赖吗？** 会 → 交付物，必须标记。

## 状态标记的落地方式

标记必须**可见、可检索、可机器校验**，三者缺一不可。

### 首选：文件内可见标记

在文件最顶部（正文之前）加一行，两种状态二选一：

```
【待审核】
```

```
【已审核通过】
```

按文件类型选用合法注释语法，位置固定在文件**第一行**（若有 shebang、编码声明或 YAML frontmatter，则紧随其后）：

| 文件类型 | 标记写法 |
|---|---|
| `.md` / `.txt` | 首行直接写标记，随后空一行 |
| `.py` / `.R` / `.sh` / `.jl` | `# 【待审核】` |
| `.js` / `.ts` / `.c` / `.cpp` / `.java` | `// 【待审核】` |
| `.tex` | `% 【待审核】` |
| `.html` / `.xml` | `<!-- 【待审核】 -->` |
| `.yaml` / `.yml` / `.toml` / `.Rproj` | `# 【待审核】` |
| `.sql` | `-- 【待审核】` |
| `.csv` / `.tsv` | 加一列 `ai_review_status` 并逐行填状态；不便改结构时改用伴随标记文件 |
| `.json`（不支持注释） | 不写注释（会破坏解析），改用顶层键 `"_ai_review": "待审核"`，或改用伴随标记文件 |
| `.docx` / `.xlsx` / `.pptx` / `.pdf` / 图片 | 无法内嵌注释，使用伴随标记文件 |

**不得为了放标记而破坏文件**。JSON 塞注释、CSV 塞注释行导致解析失败、PDF 元数据写得让工具报错——都属于把合规做成了故障。

### 伴随标记文件（无法内嵌时）

同名加后缀，与目标文件同目录：

```
figures/fig2.png
figures/fig2.png.ai-review      ← 内容为单行：【待审核】
```

### 兜底：清单文件

工作区根目录维护 `.ai-review/manifest.json`，作为权威状态源与机器校验依据：

```json
{
  "version": 1,
  "files": [
    {
      "path": "manuscript/draft.md",
      "status": "待审核",
      "marker": "inline",
      "generated_at": "2026-02-14T10:20:00+08:00",
      "last_modified_at": "2026-02-14T10:20:00+08:00",
      "approved_at": null,
      "approved_by": null,
      "note": "由本 agent 生成的初稿，含 AI 撰写的讨论段落"
    },
    {
      "path": "figures/fig2.png",
      "status": "已审核通过",
      "marker": "sidecar",
      "generated_at": "2026-02-13T16:05:00+08:00",
      "last_modified_at": "2026-02-13T16:05:00+08:00",
      "approved_at": "2026-02-14T09:12:00+08:00",
      "approved_by": "用户（会话内明确指令）",
      "note": "用户确认：'fig2.png 已确认通过'"
    }
  ]
}
```

**状态优先级（冲突裁决）**：文件内标记 > 伴随标记文件 > 清单。三者不一致时，取**最保守**的状态（即只要有任一处显示【待审核】，整体即为待审核），并在交付说明中报告不一致，请用户澄清后修正。

### `.ai-review/` 必须进入版本控制

`.ai-review/manifest.json` 与 `.ai-review/log.jsonl` 是**团队的审核记录**，不是本机私有状态。二者必须纳入版本控制并随交付物一同提交，使团队可审阅：谁在何时、依据哪句指令、批准了哪个版本的哪个文件。

- **不写入 `.gitignore`。** 发现 `.gitignore` 中存在忽略 `.ai-review/`、`.ai-review` 或 `*.ai-review` 的规则时，指出该规则与本规范冲突并询问用户是否移除；确认后再移除，不得擅自改动。注意 `*.ai-review` 这类通配规则会连带忽略**伴随标记文件**，导致协作者看不到任何状态标记——这比忽略清单更危险，须优先排查。
- **状态变更必须随交付物一起提交。** 标记与清单的变更不能游离于内容提交之外。提交交付物时，同一提交内必须包含相应的 `.ai-review/` 变更，使"内容 X 通过审核"这一事实与该内容绑定在同一个可追溯的提交里。审核记录与内容分属两个提交时，历史会失去可读性。
- **新仓库首次建立 `.ai-review/`** 时，用独立提交引入清单骨架，使其与内容变更分离，历史更清晰。
- **老仓库首次启用** 时，对现存交付物逐项补标与补登记，同样以独立提交完成；未补标的历史文件按【待审核】处理，不得默认视为已审核。

### 状态变更留痕

每次状态变更向 `.ai-review/log.jsonl` 追加一行。清单保存当前状态，日志保存"谁在何时基于哪句指令批准了什么"——合规审计要的正是后者。

```json
{"ts":"2026-02-14T09:12:33+08:00","path":"figures/fig2.png","from":"待审核","to":"已审核通过","trigger":"用户指令：'fig2.png 已确认通过'"}
```

## 工作流程

### A. 生成或修改交付物后（标记）

1. 创建/修改文件时，**在写入内容的同时**加【待审核】标记。不要"稍后补标记"——稍后通常等于忘记。
2. 在 `.ai-review/manifest.json` 中登记或更新该条目（未审核则 `approved_at` 为 `null`）。
3. 在交付给用户的回复中**明确列出**本次新增/修改的待审核文件清单，方便用户后续点名确认。

### B. 用户下达审核指令时（升级）

1. 从用户话语中**具体定位文件**。用户说"稿件已确认"，需确认指的是哪个文件；含糊时询问，不要自行推断范围。
2. 只改被点名的文件。用户批准了 A 文件，不等于批准了同时交付的 B 文件。
3. 更新标记：改文件内标记为【已审核通过】（或伴随文件），更新清单的 `status`/`approved_at`/`approved_by`/`note`（`note` 中**原样引用**用户的批准指令）。
4. 追加 `.ai-review/log.jsonl` 条目。
5. 回执确认："已将 X 标记为【已审核通过】，依据：'<用户原话>'。其余 N 个文件仍为【待审核】。"

**明确不构成审核通过的情形**：

- "看起来不错""可以""继续"——属于对过程的认可，不构成对文件内容的审核。
- "都挺好的"出现在未指名具体文件时。
- 用户此前批准过同一文件的旧版本。
- 用户批准了同一目录下的其他文件。
- 用户授予了全部权限或说"你决定"。

拿不准时一律维持【待审核】并询问。**漏批的代价是返工，误批的代价是把未经审核的 AI 产出当成定稿发布出去。**

### C. 提交前（闸门）

这是本 skill 的核心。执行顺序不可颠倒：

1. **枚举待提交文件**：`git status --porcelain` + `git diff --cached --name-only`，得到本次将进入提交的完整清单（含已跟踪文件的修改）。
2. **逐项判定状态**：查文件内标记、伴随标记文件与清单。未标记的交付物按【待审核】处理（**默认保守**）。
3. **无待审核文件** → 可继续提交流程，并在提交正文中注明已通过审核闸门。
4. **存在待审核文件** → **立即中止提交**，不得执行 `git add` 后的 `git commit`。向用户报告：

```
⛔ 提交已暂停：发现 3 个文件处于【待审核】状态

待提交清单中的待审核文件：
  1. manuscript/draft.md        （文件内标记）
  2. figures/fig2.png           （伴随标记）
  3. analysis/clean.py          （清单登记，未标记）

请逐一确认哪些文件已经审核通过。回复格式示例：
  "draft.md 和 clean.py 已确认通过，fig2.png 还没看"

在你明确确认之前，我不会提交这些文件。
```

5. **等待用户明确确认**，然后对每个被确认的文件执行升级（走流程 B），未被确认的文件继续保持【待审核】。
6. **再次核查**后提交。若用户拒绝审核某些文件，提供选项而非擅自决定：

   - （a）仅提交已通过审核的文件，待审核文件留在工作区
   - （b）暂停提交，等你完成审核
   - （c）将待审核文件从本次提交范围中排除（需说明排除方式，如 `git add` 精确指定路径）
   - （d）用户明确要求"先提交待审核版本"——此时**必须**提示该提交将包含未审核的 AI 内容，具有合规风险；用户坚持时按其要求执行，并在提交正文中醒目标注 `AI-Review: 包含待审核内容，经用户明确要求提交` 与对应 issue 引用

   **无论走哪个选项，本次提交都必须同时包含 `.ai-review/manifest.json` 与 `.ai-review/log.jsonl` 的相应变更**，让审核记录与内容同步进入仓库供团队审阅。

7. **提交后复核**：确认进入提交的文件与批准清单一致，没有多带文件。若有偏差，如实报告。

### D. 任何形式的对外发布前（闸门延伸）

投稿、上传数据集、发送给合作者、生成外部报告——这些不可撤销的对外动作在合规上比 commit 更敏感，本 skill 同样适用。发布前核对全部相关文件均为【已审核通过】，否则暂停并询问。不要因为"用户只是让我导出 PDF"就跳过闸门。

## 边界

- **不代替用户审核。** 本 skill 负责标记与拦截，不负责判断内容是否正确。不可因"我已核查过内容无错误"而自行升级状态——技术正确性与人工审核是两件事，后者是责任归属问题。
- **不擅自扩大或缩小审核范围。** 只对被明确点名的文件变更状态。
- **不因交付压力降级。** 用户催促、说明天要投、说"先这样"都不是升级状态的理由。
- **不批量批准。** 除非用户逐个点名或明确列出文件清单，否则不做批量操作。
- **不与工作区留痕规范冲突。** 本 skill 对文件标记与 `.ai-review/` 的读写属于工作区变更，应记录在工作区审计文件中；但 `.ai-review/` 内部的管理性文件（清单、日志本身）不逐条记录。标记是**内容的一部分**，不是工程文件，清理工程文件时不得删除标记。
- **不假设标记存在。** 未标记的交付物按【待审核】处理，不按"可能已被批准"处理。

各文件类型的标记范例、清单 schema、不一致状态处置与完整场景演练见 `references/review-gate-playbook.md`。
