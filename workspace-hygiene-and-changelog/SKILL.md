# 科研工作区整洁与留痕

在真实科研流程里，Agent 会为了"感知世界"生成大量一次性文件：提取 PDF 文本的脚本、转换出的中间 CSV、临时图片、调试用的 notebook、缓存目录。这些文件在交付时若被留在工作区，会污染项目、让协作者误判哪些是资产，并在后续复现时制造歧义。

本 skill 规定两件必须做的事：

1. **交付前清场** —— 本次任务产生的不必要工程文件必须被删除。
2. **全程留痕** —— 每次对工作区做出更改，都要在统一的审计文件里追加一条记录。

两件事都是默认执行，不需要用户提醒或授权确认。若与本 skill 冲突的用户指令出现（例如明确要求保留某个脚本），用户指令优先，但该例外本身要写进审计记录。

## 常态化生效

本 skill 一旦存在于项目文件中即常态生效，不依赖用户显式提及。因此：

- 在每个涉及工作区读写的任务**开始时**声明一次本次启用的规范（一句话即可，例如"按工作区规范，交付前会清理过程文件并追加审计记录"），然后直接照做，不要为流程本身反复征求同意。
- 若某个任务完全没有产生文件变动（纯问答、纯检索），不写审计记录。
- 不因"这次改动很小"而跳过记录。小改动恰恰是事后最难追溯的。

## 文件三分类

动手前先给工作区里每个新出现的文件归类。判定不清时按更保守的一类处理。

| 类别 | 定义 | 处置 |
|---|---|---|
| **工程文件（artifact）** | 为完成任务而生成、任务结束后无独立价值：临时脚本、抽取的中间文本/CSV、缓存、日志、调试 notebook、下载的依赖、格式转换的中间版本 | 本次任务结束前删除 |
| **交付物（deliverable）** | 用户实际想要的最终结果：报告、图表、数据集、整理后的表格、稿件 | 保留，在审计记录中登记 |
| **证据链（provenance）** | 支撑交付物结论、删除后即难以复现的产出：关键分析脚本、定稿图表的数据表、文献检索结果 | **保留，不得删除**；在记录中标注为证据链 |

关键判据只有一条：**删除后能否从留存的东西重新得到它？** 能，就是工程文件；不能，就是交付物或证据链。

科研场景的三条硬性例外，任何情况下都不删除：

- 用户提供的原始输入（原始数据、PDF、样本表）。
- 已登记的交付物与证据链。
- 版本控制相关内容（`.git/`、`.gitignore`、已跟踪文件）。是否删除某文件由工作区规范决定，不由 git 状态决定；不确定时询问。

## 审计留痕

工作区根目录建立 `.workspace-log/`，其中只放**一个**文件：

```
.workspace-log/
└── audit-log.jsonl
```

- **只增不改**：每次会话的每次工作区变更追加一行 JSON，绝不重写历史行。条目数随修改次数单调增加。
- **本目录自豁免**：在 `.workspace-log/` 内维护审计文件本身所产生或删除的临时文件，不记录。
- **不追加子文件**：不建索引、不分页、不按月切分。用户要求"单个文件"，就保持单个文件。

单行 JSON 的字段定义：

```json
{"ts":"2026-02-14T10:32:07+08:00","session":"pdf-extract-2026-02-14","task":"从 3 篇 PDF 提取方法学段落并汇总","created":[{"path":"scripts/extract_pdf.py","purpose":"pypdf 批量抽取正文","status":"deleted"},{"path":"out/methods.md","purpose":"三篇方法学段落汇总","status":"delivered"}],"deleted":[{"path":"tmp/pdf_pages/*.png","purpose":"版面分析中间图"},{"path":"scripts/extract_pdf.py","purpose":"一次性抽取脚本，已用毕"}],"modified":[{"path":"data/lit_matrix.csv","purpose":"新增 3 行文献条目"}],"notes":"用户要求保留原始 PDF，未做任何删除；tmp/ 已清空"}
```

字段规则：

- `created` / `deleted` / `modified` 三个数组按实际发生填写，无内容写 `[]`，不得省略字段。
- 每条目的 `purpose` 必须写清"这文件是干什么用的"，而不是只写文件名。
- `created` 中的条目若后来被删除，保留在 `created` 里并标 `"status":"deleted"`，同时出现在 `deleted` 里。这样一条记录就能读出"创造了又清掉了"的完整轨迹。
- `notes` 用于写例外、未决事项、以及任何"我判断了但拿不准"的地方。
- 时间戳用带时区的本地时间（ISO 8601）。
- 路径用相对工作区根目录的 POSIX 风格斜杠。

文件不存在时创建；文件存在时追加。若环境无法追加（只读、权限不足），不要静默跳过——明确告诉用户留痕失败及其原因。

## 执行流程

### 阶段一：开工前

1. 快速盘点工作区，记住现有的关键路径，作为交付时"哪些是我新增的"的基线。
2. 与用户确认（若尚未明确）三件事：原始数据在哪、最终交付什么、有没有必须保留的过程产物。只问真正缺失的，不要为了流程凑问题。
3. 若工作区内含 git 仓库且 `.gitignore` 存在但没有忽略 `.workspace-log/`，在根 `.gitignore` 追加一行 `.workspace-log/`。这是对用户文件的改动，须在 `modified` 中记录。
   - **例外**：团队审核记录目录（如 `.ai-review/`）必须留在版本控制中，不得加入 `.gitignore`。发现 `.gitignore` 里已有忽略它的规则时，不要自行移除，而是指出冲突并询问用户——两套规范冲突时，审核记录进仓库。

### 阶段二：工作中

- 工程文件集中放在一个明确的一次性目录（如 `tmp/`、`.scratch/`），不要散落在交付目录里。这样清理是可验证的，而不是靠回忆。
- 每完成一个阶段性动作后即清理该阶段的过程文件，不要全部堆到最后。任务中途被中断时，这样至少前半段是干净的。
- 每次工作区变更后立刻写审计条目，不要攒着。攒着写等于漏写。

### 阶段三：交付前清场

1. **列清单**：列出本次任务中自己创建/修改/删除的全部路径。
2. **分类**：逐条套用上面的三分类。
3. **验证再删**：
   - 删除前确认路径，尤其是通配符删除（`rm -rf tmp/*`）的范围。递归删除前先列出将被删除的内容。
   - 确认待删文件不是交付物、证据链、用户输入，也不是被交付物引用的资源（例如报告里引用的图片、脚本里 `source()` 的依赖）。
   - 确认待删文件不在版本控制中且未提交过——若已提交，删除会产生额外 diff，需在记录中说明。
4. **执行删除**，然后校验清场结果：一次性目录应为空或已移除；工作区内不应残留本次任务的临时文件。
5. **写审计记录**：一条 JSON 行，覆盖全部 created / deleted / modified / delivered。
6. **交付时说明**：在给用户的回复里用两三句话交代"产生了哪些过程文件、已清理哪些、留下哪些、为什么留"，并指出审计记录的位置。

### 阶段四：收尾检查表

交付前逐条自问，任何一条为"否"就回到对应阶段：

- [ ] 本次创建的工程文件是否已全部删除？
- [ ] 一次性目录是否已清空或移除？
- [ ] 是否误删了证据链、用户输入或交付物引用的资源？
- [ ] 审计文件是否已追加本次条目（含 `purpose` 字段）？
- [ ] 审计记录中的 created/deleted/modified 是否与实际文件系统状态一致？
- [ ] 向用户的交付说明是否交代了清理与留存情况？

## 拿不准时的处理

- **判断不了某文件是工程文件还是证据链** → 归为证据链，保留并记录，在 `notes` 里写明理由。误留的代价远小于误删。
- **用户说"所有权限都给你"** → 这是执行授权，不改变分类规则，也不豁免留痕。
- **删除会破坏可复现性** → 不删，改为把它登记为证据链并告知用户。
- **同一文件既是过程又是成果**（例如一次性脚本后来被要求长期复用）→ 保留，并升级为交付物，在记录中说明状态变更。
- **任务被中断** → 仍要为已发生的改动写记录；在 `notes` 中标注"任务未完成，残留 X 等待后续处理"。

## 边界

- 本 skill 不决定科研结论的正确性，只负责文件整洁与可追溯。
- 不删除用户未授权范围内的工作区之外的文件。
- 不因整洁而牺牲可复现性——这是本 skill 的第一优先级冲突裁决规则。

细节规则、完整 JSON 示例与边界案例见 `references/artifact-taxonomy.md`。
