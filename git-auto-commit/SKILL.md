# Git 自动提交

用户把提交任务交给你时，"是否执行 commit"已经由指令本身回答了——**不要再问一遍要不要提交，直接做**。需要用户决策的只有两件事：冲突如何处理，以及是否 push。

## 核心行为约定

| 环节 | 行为 |
|---|---|
| 用户要求提交 | 立即执行 add + commit，不再确认 |
| commit message | 必须同时有 summary（简短）与 description（详细），不得留空 |
| 提交后遇冲突 | 先自行分析，给出建议，**再**问用户是否按建议处理 |
| 无冲突 / 冲突已解决 | 询问用户是否 push，不自行推送 |
| 冲突未获用户同意处理 | 停在原地，保留现场，报告状态 |

## 执行流程

### 第一步：提交前勘查（只读）

在任何写操作之前搞清楚现状：

```bash
git rev-parse --is-inside-work-tree          # 是否在 git 仓库内
git status --porcelain=v1 -b                 # 当前分支、改动清单
git diff --stat                              # 未暂存改动概览
git diff --cached --stat                     # 已暂存改动概览
git log --oneline -10                        # 近期提交风格（沿用项目习惯）
git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null  # 上游分支
```

判定要点：

- 不在 git 仓库内 → 告知用户并询问是否 `git init`；若用户要提交到 GitHub，还需确认远端地址。
- 工作区干净、无未跟踪文件 → 如实报告"没有可提交的改动"，不要制造空提交。
- 存在未完成的 merge/rebase/cherry-pick（`.git/MERGE_HEAD` 等）→ 先处理这个状态，不要叠加新提交。
- 有未暂存的改动 → 全部纳入本次提交（除非用户指定只提交部分）。
- **沿用项目的提交信息语言**：看 `git log` 最近几条是中文还是英文，保持一致。

### 第二步：安全检查

- **误提交风险**：扫描待提交内容中是否有密钥、令牌、凭证、.env、大数据文件、模型权重、个人隐私数据。
- 命中时应暂停并告知用户，而不是直接提交。真的必须提交时，明确提醒这会进入仓库历史，清理成本很高。
- 确认 `.gitignore` 是否覆盖了构建产物、缓存、临时目录。
- 留意是否有超大文件（仓库体积不可逆增长）。

### 第三步：暂存与撰写提交信息

```bash
git add -A          # 或按用户指定范围添加
git diff --cached --stat    # 暂存后复核，确认没夹带无关文件
```

**Summary（简短）**——Conventional Commits 风格，≤ 72 字符，动宾结构，不加句号：

```
<type>(<scope>): <subject>
```

常用 type：`feat` 新功能 / `fix` 修 bug / `docs` 文档 / `refactor` 重构 / `perf` 性能 / `test` 测试 / `build` 构建与依赖 / `ci` 流水线 / `chore` 杂项 / `data` 数据更新 / `analysis` 分析脚本变更 / `revert` 回退。

Scope 可省略。科研项目里 scope 常用模块或稿件名，例如 `analysis`、`fig2`、`manuscript`。

**Description（详细）**——正文，回答三个问题：

1. **改了什么**：具体到文件或模块，不要复述文件清单。
2. **为什么改**：动机、触发原因、解决的问题。
3. **影响范围**：会影响到谁/哪部分流程；有无破坏性变更、需要重建或重跑什么。

正文格式：

- 与 subject 之间空一行。
- 分条陈述，每条以 `-` 开头，一条一个要点。
- 需要时附上关键文件路径、命令、数据版本。
- 破坏性变更以 `BREAKING CHANGE:` 开头单独成段。
- 关联议题写在末尾，如 `Refs: #12` 或 `Closes: #12`。

提交命令（多行信息用多个 `-m`，避免 heredoc 在各平台上的差异）：

```bash
git commit -m "feat(analysis): 新增样本量估算脚本" \
           -m "- 增加 power_analysis.py，支持 t 检验与卡方检验的效能计算
- 输入参数从 config.yaml 读取，避免硬编码
- 现有流程无需改动，脚本为独立入口

Refs: #12"
```

**反面写法**（不要这样提交）：subject 写成 `update`、`修改`、`fix bug`；正文留空；正文只重复文件名清单；把大段 diff 贴进正文。

### 第四步：提交并检查结果

```bash
git commit ...      # 按上一步
git log --stat -1   # 复核本次提交内容与信息
git status          # 确认工作区状态
```

若提交失败（pre-commit hook 拦截、user.name/email 未配置、GPG 签名失败等）：

- 读取报错原因，区分"代码问题"与"环境配置问题"。
- 环境配置类（缺 user.name/email）可自行修复后重试。
- hook 报错涉及代码质量时，如实报告问题，不要用 `--no-verify` 绕过；确有必要时先征求用户同意。
- 不擅自 `--amend` 已推送的提交。

### 第五步：冲突处理

冲突可能出现在 push 被拒后的集成（fetch + merge/rebase）阶段，或存在于提交前的仓库状态中。**一旦出现冲突：先分析，再询问，不擅自解决。**

分析必须产出以下内容：

1. **冲突范围**：哪些文件冲突、各有多少处冲突块。
2. **冲突成因**：两边各自改了什么，是因为同一函数被并行修改、文件被重命名/移动、还是删除与修改相遇。用 `git log --oneline --left-right HEAD...MERGE_HEAD`（或 `@{u}`）看清双方提交。
3. **逐块判读**：对每处冲突说明 `<<<<<<< ours` 与 `>>>>>>> theirs` 两侧的语义差别，指出哪一侧更可能是正确的意图，以及理由（谁更晚、谁更完整、谁与当前主线一致性更高）。
4. **建议方案**：给出具体到文件与冲突块的处理建议，包括是否需要两侧都保留、是否需要改写逻辑而不仅是二选一。
5. **风险提示**：说明采纳建议后可能丢掉什么改动，以及验证方法（跑测试、编译、核对功能）。

然后**询问用户是否按建议处理**，给出可选项：

- （a）按建议全部解决
- （b）只解决指定文件，其余保留冲突标记交由用户处理
- （c）放弃本次集成，回到集成前状态（`git merge --abort` / `git rebase --abort`）
- （d）用户自行修改后告知你继续

用户未答复前不要动冲突文件。用户拒绝建议时，不要换个说法重提同一方案；记录其理由并调整。

解决完成后验证：搜索残留冲突标记（`grep -rn -E "^(<<<<<<<|=======|>>>>>>>)" .`），跑项目测试或构建，再 `git add` 与提交（若是 rebase 则 `git rebase --continue`）。

### 第六步：询问是否 push

在**无冲突**或**冲突已解决并提交**之后，暂停并询问用户是否 push。给出必要信息帮助决策：

- 当前分支与目标远端分支（如 `main` → `origin/main`）
- 本次将推送的提交条数与摘要
- 远端是否有新提交、是否会出现 non-fast-forward
- 是否推送到非默认分支

用户同意后执行：

```bash
git push            # 已有上游
git push -u origin <branch>   # 首次推送，建立上游
```

**绝不使用 `--force`**，除非用户明确要求且你已说明会覆盖远端历史。远端有新提交时，走 fetch + rebase/merge → 再回到冲突处理流程。

push 完成后报告：推送的分支、提交哈希范围、远端地址。

## 与用户沟通的节奏

一次提交任务向用户提出的问题应当**最多两次**：冲突如何处理（仅在有冲突时）、是否 push。其余环节自行完成并汇报。

交付时用简洁格式说明：

```
提交完成：a1b2c3d  feat(analysis): 新增样本量估算脚本
  - 3 个文件变更，+128 / -14
  - summary 与 description 已按规范填写
冲突：2 个文件 4 处冲突，已分析并给出建议（详见上文），等待你的决定
push：尚未推送，等你确认后再执行
```

## 边界

- 不自行 push。这是本 skill 唯一保留给用户的执行决策。
- 不自行解决冲突。分析与建议由你完成，决定权在用户。
- 不提交疑似机密与超大数据文件。
- 不 `--amend` 已推送的提交，不 `rebase` 共享分支上的已推送提交，不 `--force`。
- 不因提交失败而擅自回滚用户的工作区改动（`git checkout .`、`git reset --hard` 一律需要用户明确要求）。
- 提交动作属于工作区变更，应配合工作区留痕规范记录（涉及哪些文件、提交哈希、以及过程中产生的临时文件是否已清理）。
